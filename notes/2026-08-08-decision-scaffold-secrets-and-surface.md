# Decision — credentials and runtime surface (2026-08-08)

Three gaps found by auditing the `api/` scaffold (issue #1) rather than by
designing. Two of them are rules the security record never made, because it
was written on 2026-07-30 — before there was a datasource to configure or a
springdoc dependency to choose. Amends
`notes/2026-07-30-decision-network-security.md`; does not replace it.

## A secret never travels inside a connection string

The workspace convention stores one `DATABASE_URL` per project in the shape
`postgresql://<role>:<password>@127.0.0.1:5432/<db>`. For a Spring app that
is wrong twice over, and the second reason is the one that matters.

The shallow reason: `spring.datasource.url` needs a JDBC URL, so the app
simply does not start on a `postgresql://` value.

The real reason: HikariCP's failure path is
`RuntimeException("Failed to get driver instance for jdbcUrl=" + jdbcUrl)`.
So the **first** bad startup prints the password — to stdout, to the log
file, and into whatever startup-failure paste ends up in an issue or a chat.
The security record already says secrets are "masked in logs and error
messages"; nobody had noticed that a connection string is a place a secret
can hide from that rule.

**Rule: a secret that must not be logged is never embedded in a connection
string. One sealbox key per credential component.** For `donghaeng`:

| Key | Value |
|---|---|
| `donghaeng/DATABASE_URL` | `jdbc:postgresql://127.0.0.1:5432/donghaeng` — credential-free |
| `donghaeng/DB_USERNAME` | the role |
| `donghaeng/DB_PASSWORD` | the password |

Bound to `spring.datasource.url` / `.username` / `.password`. Spring never
echoes the latter two as part of the URL, so the Hikari failure path has
nothing to leak. The original URI-form value survives as `DATABASE_URL@v1`
in sealbox — nothing was destroyed.

This is a documented **exception to the workspace pattern** in
`../../notes/local-infra.md`, recorded there too. The exception is
Spring-specific; it does not generalise to every project.

## No machine-readable introspection surface is internet-reachable

The security record says "Spring Boot Actuator is never exposed to the
internet." Written before springdoc was chosen, it names the instance rather
than the category — and springdoc is the same category with a friendlier
name. `springdoc.api-docs.enabled` defaults to **true**, and the dependency
is a normal `implementation` one, so a deploy would publish a complete
machine-readable map of every endpoint, parameter, and DTO field — including
the session and invite-token routes — to anyone who asks for
`/v3/api-docs`.

**Rule, widening the old line: no machine-readable introspection surface —
Actuator, `/v3/api-docs`, Swagger UI — is reachable from the internet.**
`api-docs` is disabled by default and enabled only where the document is
actually generated, which is the build, not the running service. The seam
needs that document at build time; it never needs it live.

Swagger UI stays off the classpath entirely (`springdoc-openapi-starter-webmvc-api`,
not `-ui`), and Actuator is not a dependency at all.

## Postgres 16 is the production major

Tests pinned `postgres:16-alpine` before anything decided that. Ratified:
**16**, matching the local cluster (16.13). This is worth pinning early
rather than at deploy time for one reason — the native aggregation queries
are the place where a version difference produces a *different number*
rather than an error, and a wrong headcount that never throws is the failure
this product can least afford.

## Smaller item

The committed Gradle wrapper jar did not match the pinned distribution
version (authentic Gradle, generated by a locally installed 9.6.1 while
`distributionUrl` pinned 8.14.3 — it works, since the jar is a
version-agnostic downloader, but nothing in the repo said so). Regenerated
so they agree, with `distributionSha256Sum` pinned. `gradle/actions/wrapper-validation`
belongs in CI (#36) so this is a gate rather than an audit someone happens
to run.
